# ParadigmEve private dogfood release candidate

## 2.2.2

This candidate is the **cumulative continuation of 2.2.1**. It retains the accepted 2.2.1 model
selection, Activity/Pins/Thread, starter-durability, Thread-description, accessibility and browser-
recovery work, then finalizes the current `%schedules` and `%requests` product slices and carries a
bounded Computer Use recovery hardening pass. It is a private/local dogfood candidate: source and
package checks prove ParadigmEve's own ownership rules, while installed dogfood must separately prove
the live schedule, request-continuity, and Computer Use flows.

Git provenance is part of this candidate's evidence. The cumulative source must be checkpointed on a
2.2.2 branch with both 2.2.1 and 2.2.2 release notes tracked before packaging; version strings alone
do not prove that the 2.2.1 baseline was carried forward.

Bridge protocol remains **15** because these changes do not require an incompatible app/Companion
browser-wire contract.

## What changed

### Durable schedules and truthful execution

- `%schedule` owns the user's durable availability. Availability remains explicitly known or
  unknown; ParadigmEve does not invent free time from missing data.
- `%evecron` owns durable Eve schedule entries, including explicit duration, recurrence/one-time
  timing, task text, and active/paused state. Create/edit/pause/resume mutations use the durable
  schedule authority rather than a renderer-side copy.
- The shared Schedule editor for **Your availability** and **Eve routines** uses the current app
  theme surfaces for its dialog, inputs, and secondary text. The editor therefore keeps an opaque,
  readable backplate in both light and dark themes instead of becoming transparent when obsolete
  theme variables are unavailable.
- Schedule projection uses explicit user availability and explicit Eve duration. Shared-free time is
  shown only when the backend can resolve it truthfully; missing duration or unresolved availability
  remains **Not available yet** instead of being guessed.
- Automatic maintenance admits only due, already-authorized installation-agent occurrences.
  Scheduled work opens in a separate fresh schedule lane and must not hijack or append to the user's
  active chat.
- **Started** requires durable browser-delivery evidence: the exact scheduled input is accepted by
  the browser and matches the recorded fresh session. Queue/claim state alone is not Start.
- **Done** requires durable completion/verification evidence followed by the schedule completion
  transition. Assistant prose, elapsed time, a sent message, or a worker finishing is not sufficient.
- Stable occurrence/input identities make admission and Started/Done receipts restart-safe and
  idempotent.

### Durable requests, exact continuity, and review authority

- Long-running accepted work can create a durable Request Trail that preserves the original request
  and its lifecycle across restart.
- Request check-ins use durable revision/claim state so recovered progress or review-ready
  notifications do not duplicate after restart.
- Request/result surfaces retain exact references to the originating request, owning Thread, Plan,
  result, tests, and current review/signoff state. The native request notification returns to the
  exact recorded originating request event rather than merely the containing conversation.
- When a request has an exact owning Thread, that Thread becomes the Plan's primary Source/context
  anchor. Historical session/message provenance remains evidence and fallback, not the preferred
  navigation target.
- Exact `%Thread` references open that Thread by durable identity; exact `#Quilt` references open
  the wider Quilt context. Missing or ambiguous references fail closed.
- Checking the final Plan item means implementation is complete and may become **Ready for review /
  Ready to archive**. It does not record user signoff and does not auto-archive the Plan.
- User signoff is recorded only by the explicit Plan archive action. Until then the completed Plan
  remains Live.

### Computer Use accessibility and recovery focus

- Windows accessibility/UIA enablement is established before UIA-dependent observation so a valid
  target is not falsely reported unusable merely because accessibility was initialized too late.
- Installer/recovery handling may retry a focus failure only within the bounded recovery path and
  only for the exact dedicated Eve Browser profile/window. It re-acquires that target and retries
  rather than weakening ordinary Computer Use focus checks.
- The recovery retry is bounded and fails closed. It does not open an unrelated fallback browser
  window/tab, does not use browser chrome privacy surfaces, and does not relax normal input
  target/focus authority.
- Managed restart recovery now fences readiness to the current recovery attempt. Evidence that was
  already warm before Chrome restarted cannot satisfy `/recovery`; the replacement Companion must
  publish a fresh current-generation document/census after the restart boundary, and when durable
  Eve/Eva identity proves one exact recovery conversation that fresh census must contain that exact
  conversation before recovery is considered ready.
- Recorder-attribution reconnect remains retryable while a fresh worker/Resume journal gate is
  intentionally closed. A gated or incomplete request-id replay no longer consumes the reconnect
  token; the same exact page retries after rebind and the token is retired only after `/correlations`
  confirms the request ownership. This keeps exact caller authority fail-closed without reloading or
  navigating a healthy generating page.

## Current candidate identity

The package, lockfile root package, bundled `APP_VERSION`, Companion manifest, current Vault, and
these release notes must all identify **2.2.2** before packaging. The Windows installer gets its
product version from the package metadata, so there is no separate installer-only version to bump.

The laptop/local dogfood artifact is a Windows x64 **debug** installer:

- `ParadigmEve-Setup-x64-debug.exe` — Windows x64 debug installer.

The filename is intentionally versionless. Prove the 2.2.2 identity from package/runtime metadata,
the Companion manifest, packaged smoke evidence, installed executable/runtime evidence, and the
archived checksum record.

## Companion update boundary

Managed Windows self-reinstall materializes the packaged Companion and restarts/recovers the
dedicated browser profile automatically. Do not manually reload the Companion during that flow.
For manual or otherwise non-managed updates, reload the matching unpacked Companion only when Chrome
is still running an older Companion runtime. Connector-schema refresh in ChatGPT is a separate
operation and should run only when the current declaration requires it.

## Required acceptance before dogfood

- the focused schedule/request/Computer Use regression suites pass against the frozen tree;
- fresh-install/setup acceptance passes;
- typecheck and full repository verification pass;
- package/lockfile/Companion/`APP_VERSION`/Vault/release-note metadata all agree on 2.2.2;
- the Windows x64 debug NSIS build finishes successfully;
- packaged-runtime and installer Vault smoke checks pass against the produced payload;
- the installer and blockmap are hashed and archived as 2.2.2 evidence;
- installed runtime behavior is verified separately from source/test/build success.

A passing unit seam cannot waive a missing production caller. Before building, the installed-dogfood
wiring gate must show that schedule maintenance is started/drained, browser ACK reaches schedule
Start reconciliation, real completion evidence can reach schedule Done, accepted long-running work
reaches Request Trail, the production check-in owner/notifier is wired, exact original-request
navigation is preserved, the exact originating Thread can become the Plan's primary Source, and only
explicit Plan archive records user signoff. `update_plan` remains projection-only and does not own
human Plan archive/signoff.

## Installed dogfood boundary

For schedules, prove the installed app can create/edit/pause/resume durable availability and Eve
work, project overlap without inventing free time, keep an ordinary user chat untouched while a due
schedule opens separately, emit one ACK-backed **Started**, emit one evidence-backed **Done**, and
survive restart without duplicate admission.

For requests, prove a fresh chat can start from the exact `%requests` Thread, the Plan Source opens
that durable Thread, exact request/result/test evidence can be reached through the recorded source
identities, the native request notification returns to the exact originating request event, the final
checklist item leaves the Plan Live as **Ready to archive**, and restart preserves the trail without
duplicate check-ins. Installed dogfood stops at the user signoff boundary: the explicit archive
control must be present, but signed-off state must not appear unless the user later archives the Plan.

For Computer Use, prove semantic accessibility is available for the installed ParadigmEve window and
that recovery-only focus retry can re-acquire the exact Eve Browser target after a focus failure
without weakening ordinary Computer Use focus rules or opening a fallback browser target. Managed
restart recovery must also stay unready on stale/pre-restart Companion evidence, wait for a fresh
post-restart census containing the exact durable Eve/Eva owner when one exists, and preserve
request-id attribution through a temporarily gated recorder reconnect without consuming its retry.

## Platform notes

The release binaries are **unsigned**; macOS builds are also **unnotarized**. macOS requires
**macOS 13 Ventura or newer**. Ad-hoc sealing verifies bundle integrity but does not establish
publisher trust, so verify the matching SHA-256 checksum before running a downloaded artifact.

On Linux, prefer the DEB on Debian/Ubuntu. If a host disables **unprivileged user namespaces**,
the AppImage launcher can use its documented conditional `--no-sandbox` fallback. That fallback is
not the default launch mode.
